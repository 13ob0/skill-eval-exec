# eval-exec

评估-执行

> 先评估，获得明确批准后再执行。

[English](README.md) | **简体中文**

`eval-exec` 是一个供编码代理使用、通过 agent 工具调用的小型工作流 skill。
它将基于证据的评估与实施分开，让用户可以在代理修改文件、配置、数据或
外部状态前，先审阅计划范围。

## 为什么使用它？

变更请求通常隐藏着一些重要问题：真正的瓶颈在哪里、哪些现有路径可以复用、
哪些语义或风险需要关注，以及如何验证成功？`eval-exec` 会明确这些问题，
同时避免让每次对话都变成一轮冗长的计划会议。

模型具备很强的代码生成能力，但“能写出代码”并不等于“准确理解了需求”。模型可能生成结构完整、逻辑自洽、甚至能够通过测试的实现，却仍然解决了错误的问题，或者采用了用户并未认可的技术取舍。

换句话说，模型的能力决定了它能把一个方案执行到什么程度，但不自动决定这个方案是否符合用户真正的目标。需求中的“高性能”“安全”“兼容”等词，仍然需要结合具体场景、边界和验收标准进行对齐。

`eval-exec` 将这种方向偏差拦截在代码修改之前：先通过基于证据的评估，让模型明确表达它对需求、影响范围和实施方案的理解，再由用户决定是否执行。

评估阶段重点确认三件事：

- **目标含义**：把模糊目标转化为可判断的行为、边界和验收标准；
- **影响范围**：识别涉及的文件、接口、调用方、数据路径，以及潜在的连锁反应；
- **决策边界**：明确哪些实现细节可以由代理自行决定，哪些架构选择、技术取舍和风险必须由用户确认。

因此，评估不是为了验证模型“会不会写”，而是为了确认模型“准备写什么”。方向偏差在文本层暴露时，通常只需要调整需求理解或实施范围；一旦进入代码、测试和接口契约阶段，纠偏成本就会显著增加。

持续使用评估，也能帮助用户跟踪项目结构和变更影响，在享受模型高执行力的同时，保持对系统整体方向的控制。

## 它与完整规划流程的区别

`eval-exec` 不是完整的 Plan Mode、架构设计或 SDD 流程，而是一个轻量的执行前对齐步骤。它关注的是三个问题：

- 模型是否正确理解了当前需求；
- 模型准备采用什么实现方向；
- 这个方向有哪些主要影响和风险。

评估阶段可以进行必要的只读检查，但不会修改文件、配置、数据或外部状态。只有用户发送独立的 `execute` 或 `执行` 命令后，代理才会实施最新且未改变的评估范围。

它适合日常局部变更、需求存在歧义的任务，以及需要在动手前快速确认方向的请求。对于架构重做、复杂迁移或多人协作，应结合更完整的规划和设计流程。

如果希望评估保持轻量，可以在请求中限定输出范围，例如：只说明需求理解、关键模糊点、推荐做法、主要风险和验证方式，不生成代码、不修改文件。

工作流刻意保持简单：

1. 针对变更请求，通过 agent 工具调用 `eval-exec`。
2. 代理检查相关证据，只返回评估结果。
3. 审阅结论、证据、范围、风险和验证计划。
4. 发送独立的 `执行` 命令，批准实施。
5. 代理实施已批准的范围，完成验证并报告结果。

调用 skill 会自动开始评估，用户不需要额外附加 `评估`。

## 命令

使用规范的中文命令：

- 开始评估：通过 agent 工具调用 `eval-exec`。
- 批准实施：`执行`。

模糊的确认语句，例如 `go ahead`、`continue`、`proceed`、`sounds good`、
`do it`、`let's do it`、`好的`、`继续` 和 `可以`，不会被视为执行命令。
这样可以让不同代理运行环境中的批准保持明确。

## 评估内容

skill 会根据请求调整评估方式。典型评估包括：

- 结论和当前实现状态；
- 具体的仓库、运行时、配置、日志或测量证据；
- 按优先级排列的建议，以及说明顺序原因；
- 边界、安全问题、兼容性风险和待确认问题；
- 预计涉及的文件、接口、测试或系统范围；
- 验证步骤，以及用户可以观察到的预期结果。

评估阶段只允许进行只读检查。执行范围仅限于最新且未改变的评估；如果范围
发生实质变化，需要重新进行评估。

## 安装

### 通过 Agent 安装

把下面这句话发给你的 Agent。

> 帮我安装这个skill：[https://github.com/13ob0/skill-eval-exec](https://github.com/13ob0/skill-eval-execute)

Agent 会读取仓库、找到 **eval-exec**，完成安装。装好之后显示名为「Eval Exec」。

### Skills CLI

使用 [`skills` CLI](https://www.skills.sh/docs/cli) 从 GitHub 安装此 skill：

项目级安装：

```bash
npx skills add 13ob0/skill-eval-exec --skill eval-exec
```

Codex 全局安装：

```bash
npx skills add 13ob0/skill-eval-exec --skill eval-exec --global --agent codex
```

上述命令都会从 GitHub 拉取 skill，因此目标提交必须已经推送到远端仓库。

本仓库遵循顶层 `skills/` 目录的常规布局，skill 位于 `skills/eval-exec`。

### 手动安装

克隆或下载本仓库，然后将 `skills/eval-exec` 复制到代理的 skills 目录。
对于 Codex，目标目录通常是：

```text
$CODEX_HOME/skills/eval-exec
```

如果没有设置 `CODEX_HOME`，可以使用当前平台默认的 Codex skills 目录，通常为：

```text
~/.codex/skills/eval-exec
```

安装后启动新的代理会话，然后通过 agent 工具调用 `eval-exec`。

## 开发与打包

源文件是 `skills/eval-exec/SKILL.md`。可以使用代理环境中提供的
skill-creator 脚本进行校验和打包：

```bash
python <skill-creator>/scripts/quick_validate.py skills/eval-exec
python <skill-creator>/scripts/package_skill.py skills/eval-exec dist
```

打包产物包含 skill 目录及其中的 `SKILL.md`；README、许可证和仓库元数据
仍位于可安装 skill 之外。

## 兼容性与限制

- 工作流面向通过 agent 工具调用的场景设计。
- 是否自动选择 skill 取决于宿主环境，本仓库不保证自动选择行为。
- 英文是主要指令语言；中文命令 `评估` 和 `执行` 仍然受支持。
- 这个 gate 用于协调代理行为，不能替代沙箱、审批、访问控制或部署安全措施。
